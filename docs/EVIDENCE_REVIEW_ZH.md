## 为什么部分证据可信

- 功能答案由独立Python重新生成数据、列表和整数L2排序得到，不接受模拟器自报PASS。
- 检查事件轨迹，而非只比较最终top-k：生产后才能提交，填充后才能可见，
  读取后才能计算，消费后才能复用；HBM/HBF逻辑字节分别核算。
- 注入提前消费、错误地址、数据破坏，以及删除/重复事件，检查器必须拒绝。
- bank除参考解释器外还检查总线排斥、时序下界和信用守恒；有少量可手算案例。
- 初次bank集成的同刻pause失败、后续过期时间请求检查，以及A6000探针
  只触及部分分配内存的问题均被识别并修正，原始GPU试跑保留。

## 证据自身的局限

- Python bank参考机与C++实现使用相同规则，存在共同理解错误；不是外部硬件oracle。
- 22组读错误测试是声明式期望序列，不是独立完整设备参考机。
- 部分所谓mutation仅改变期望/结果再比较，并非真正修改实现重新运行，证据很弱；
  不能与实际注入数据破坏、提前完成等负向测试等同。
- 固定seed和toy数据覆盖有限；没有穷尽状态空间，也没有独立研究者审阅结论。
- CECC/UECC和die恢复尚未贯穿真实响应传输；refresh确认仍为注入事件。
- GPU探针只检查最终索引；没有逐次load观测，不能定位所有可能的错误。
- GPU动态时钟、缓存、TLB和互连仍影响样本；未拟合参数、未做留出集误差验证。

## 不依赖HBM硬件也应先完成的验收

1. 在A6000运行实际GPU ANNS最小流程，保存真实候选、距离、top-k、传输与同步事件，
   与CPU参考及模拟输出比较；现有pointer chase不能替代它。
2. 让读错误、retry metadata、die阻塞/解除及refresh完成贯穿同一真实模拟路径，
   覆盖并发命令、失败重试、信用释放和数据版本；不能只测孤立policy。
3. 增加与独立成熟DRAM模型的命令合法性对照，以及真正修改实现的mutation tests；
   说明仍共用哪些参数和假设。
4. 将功能正确与时序校准分别验收。现在可验证A6000访问路径，但不可把GDDR6
   拟合结果标作HBM。未来有HBM后再冻结其参数/训练与留出工作负载/误差门槛。

性能门保持关闭。当前代码适合发现协议、依赖和资源记账错误，不适合支持
QPS/P99、功耗或HBF优越性结论。
